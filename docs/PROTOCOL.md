# Протокол канала «линия связи → планировщик»

Кастомный бинарный кадр поверх сырого потока TCP/UDP. Все поля **big-endian**.
Транспортная инкапсуляция не входит в объём: парсер принимает байтовый поток и
сам находит границы кадров (magic + ресинк), как это делает промышленное
оборудование без транспортного слоя сообщений.

## Формат кадра

| Смещение | Размер | Поле | Комментарий |
|---|---|---|---|
| 0 | 2 | `magic` | `0x43 0x4D` («CM») — точка входа автомата парсера |
| 2 | 1 | `version` | `1` |
| 3 | 1 | `type` | `1` = `TRAJ_CMD` (цель перемещения), `2` = `HEARTBEAT` |
| 4 | 2 | `len` | длина полезной нагрузки координат, байт (`axes × 4`) |
| 6 | 2 | `seq` | монотонный счётчик отправителя (проверяется потребителем) |
| 8 | 4 | `ts_ms` | метка времени отправителя, мс |
| 12 | 4 | `axis_mask` | битовое поле состояния осей/подсистем (бит i = ось i) |
| 16 | 2 | `axes` | число координат в нагрузке, 0…16 |
| 18 | axes×4 | `coords` | координаты цели, формат **Q16.16** |
| −2 | 2 | `crc16` | CRC поверх всех предыдущих байтов |

Заголовок — 18 байт; максимальный кадр `18 + 16×4 + 2 = 84` байта
(`kFrameMax`). Кольцевой буфер парсера по умолчанию 256 байт
(`static_assert(RingN >= 2 * kFrameMax)` — буфер обязан вместить два
максимальных кадра, чтобы не терять границу при ресинке).

### Q16.16

Знаковое фиксированное 32 бита: 16 целых, 16 дробных. Значение = `raw / 65536`.
Диапазон координат ±32767 единиц (мм — достаточно для зоны манипулятора).
Насыщение при кодировании (`from_real`) детерминировано, без NaN-веток.

### CRC

CRC-16/CCITT-FALSE: полином `0x1021`, init `0xFFFF`, без реверсирования,
xorout `0`. Таблица 256 слов вычисляется на этапе компиляции
(`constexpr`), аллокаций в рантайме ноль.

Эталон: `crc16_ccitt("123456789") = 0x29B1` — зафиксирован `static_assert`
и сверен внешним источником (`binascii.crc_hqx(data, 0xFFFF)` в Python stdlib).
Распространённое значение `0xE5CC` соответствует другой вариации
(с аугментацией 16 нулями) и в протоколе не используется.

## Тестовый вектор

`TRAJ_CMD`, seq `0x1234`, ts `1000 мс`, `axis_mask = 0x0000000F`,
3 оси, цель `(10.0, 3.0, 0.0)`:

```text
434D 0101 000C 1234 000003E8 0000000F 0003
000A0000 00030000 00000000
1B74
```

Разбор: `len=0x000C` (3×4), `axes=0x0003`, координаты `0x000A0000` = 655360 →
`10.0`; `0x00030000` = 196608 → `3.0`; CRC кадра `0x1B74`. Изменение любого
байта меняет CRC → автомат выдаёт `CrcError` и исполняет побайтовый ресинк
к следующему magic.

## Автомат парсера

Состояния результата (`PStatus`):

- `NeedMore` — в буфере меньше `kFrameHdr + len + 2`, ждём байты;
- `Ok` — кадр валиден, заполнен `ParsedFrame` (trivially copyable, `< 512` байт,
  уходит в SPSC как часть `FrameMsg` c `alignas(64)`);
- `CrcError` — границы соблюдены, CRC не сошлась: кадр отбрасывается, точка
  чтения сдвигается за его конец (потеря кадра не ломает поток);
- `LengthMismatch` — `len` не кратен 4 или не совпадает с `axes*4`: немедленный
  побайтовый ресинк;
- `Resync` — magic не найден в пределах кадра: пропуск одного байта, повтор.

Гарантии: конечный автомат без выделения памяти; одна вызов-итерация
обрабатывает ровно один кадр или один шаг ресинка; переполнение кольца —
возврат `NeedMore = false` с отчётом, вытеснение старых данных невозможно
из-за инварианта `RingN ≥ 2·kFrameMax` при дисциплине «один кадр за вызов».

## Энкодер

`FrameWriter` (для тестов/стенда) собирает кадр в `std::array<u8, kFrameMax>`
на стеке и дописывает CRC в `finish()`. Тестовый цикл: encode → parse →
сверка полей round-trip; отдельный тест портит байт после `finish()` и
требует `CrcError`.
