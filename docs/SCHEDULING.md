# Планировщик: Job-Shop + пространственно-временные коллизии

## Модель

| Сущность | Представление |
|---|---|
| Робот | `RobotCell`: id, приоритет, лимиты `vmax/amax/jmax`, `tcp`, путь-полилиния, S-curve профиль, `t_start` |
| Зона | AABB или OBB (центр, полуоси, базис) — общая досягаемость, межроботовый буфер |
| Станок | `Machine { id, busy_until }` — монопольный ресурс |
| Операция | `schedule_job(machine, dur, ready)` → старт `max(busy_until, ready)` |

Планировщик **однопоточный**: весь мир в одном потоке, вход — очередь SPSC.
Детерминизм важнее параллелизма: одинаковый вход даёт бит-в-бит одинаковое
расписание.

## Интервал occupancy зоны

Для пары (робот, зона) вычисляется временное окно `[t_in, t_out]` пребывания
TCP в зоне:

1. **Геометрия**: пересечение каждого сегмента полилинии с боксом методом
   slab (для OBB отрезок переводится в локальный базис бокса; для AABB —
   проекции на мировые оси). Результат — дуги `[s_in, s_out]` на пути,
   включая частичные входы в сегменты.
2. **Время**: `t = t_start + traj.time_at(s)` — обратное отображение дуги
   через профиль (бисекция 32 шага, см. TRAJECTORY.md).

Это точнее попиксельной сетки и дешевле полноценного swept-volume: в задаче
«одна точка инструмента через выпуклую зону» точное аналитическое окно.

## Разрешение конфликта

Пара роботов конфликтует в зоне, если окна пересекаются (`ovl > ε`).
Жертва (`victim`) — робот с меньшим приоритетом (при равных — позже
принятый). Коррекция, в порядке возрастания стоимости:

1. **Respeed** — пересчёт S-curve жертвы с пониженным `vmax`
   (`vmax × 0.85^k`, k ≤ 6). Окно входа сдвигается вперёд, зона
   освобождается раньше соседа. Цикл не останавливается: скорость в зоне
   остаётся ненулевой.
2. **DelayStart** — фазовый сдвиг `t_start += ovl + ε` (ровно на длину
   перекрытия). Применяется, если 6 снижений не развели окна.
3. **Failed** — не сошлось: кадр отклоняется (`rejected`), исполнительный
   контур получает отказ вместо зависшего расписания.

`resolve_all` — полный обход все пар роботов × зоны, фиксированный порядок,
до 8 проходов (конвергенция: каждая коррекция монотонно сдвигает окна).
Счётчики `collisions / mit_respeed / mit_delay / mit_failed` — атомарные,
для наблюдаемости.

## Перепланирование на лету

Новая команда для **активного** робота не останавливает цикл:
`tcp` пересчитывается как фактическая позиция на текущем пути
(`path.point_at(traj.pos(now − t_start))`), новый путь строится от неё,
профиль — заново. Стартовое окно смещается на `now`.

## Job-Shop

Станки — тривиальный монопольный ресурс: очередь по `busy_until`,
старт = `max(busy_until, ready_at)`. Это ядро планирования ИТР в миниатюре:
операции не перекрываются на станке, учитывается готовность задания.
Тест проверяет монотонность и непересечение времен на 3 станка × 6 операций.

## Стоимость

Парная проверка: O(сегментов пути × 3 оси) геометрии + 2 инверсии по 32 шага.
Для 3 роботов и ≤ 8 зон — микросекунды на перепланирование; бюджет цикла
исполнения (мс) не напрягается.

## Что не решается

- Взаимные задержки в цепочках (net-free time для критических путей).
- Приоритетные инверсии по времени (robust scheduling). Демо решает
  попарно и итеративно — для трёх роботов сходятся все прогнанные сценарии,
  формальной полноты алгоритм не обещает (см. Ограничения в README).
